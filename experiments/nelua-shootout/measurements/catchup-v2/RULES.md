## Interpretation and remaining limits

- **Batch sharing:** the rule text broadly prohibits caching across requests. The selected implementation reads after its group is frozen, admits no new members while executing it, and retains no result for answering later requests. Individual response buffers naturally remain alive until their own socket finishes sending. Closely matching merged precedent is [PR #131](https://github.com/arjaythedev/multicore-server-challenge/pull/131): batch-local tags and rendering, followed by the [maintainer's explicit no-cross-request-cache assessment](https://github.com/arjaythedev/multicore-server-challenge/pull/131#issuecomment-6525086821). [PR #132](https://github.com/arjaythedev/multicore-server-challenge/pull/132) expressly describes sharing serialized payloads within one batch and was [accepted](https://github.com/arjaythedev/multicore-server-challenge/pull/132#issuecomment-6531228747). These are specific accepted precedents, **not blanket approval of this PR or arbitrary reuse**.
- **HMAC context:** the selected implementation recomputes each JWT's MAC and verification; it retains the configured key/provider state, not a previously accepted token verdict. Accepted frozen implementations retain key midstates ([#132 auth.rs:246](https://github.com/arjaythedev/multicore-server-challenge/blob/67dfe8e85ad11835df2d2fc926f9e59b50c832e9/submissions/rust-epoll-theCatWisel/src/auth.rs#L246)) or a keyed template ([#131 jwt.rs:32](https://github.com/arjaythedev/multicore-server-challenge/blob/572c19999e1a91513fc8c2431c6766870221d631/submissions/rust-epoll-WorriedArrow/src/jwt.rs#L32)). This is also the precomputation permitted by [RFC 2104 §4](https://www.rfc-editor.org/rfc/rfc2104.html#section-4).
- **Build reproducibility:** the Nelua source dependency is exactly pinned; Ubuntu's compiler/libpq/OpenSSL/libcrypt packages follow the benchmark's package repositories, rather than exact apt package-version locks. This follows the challenge's normal Ubuntu package-install model, but is not a fully hermetic build. Runtime needs only the four SPEC variables; documented optional environment switches adjust application-local settings and have working defaults.
- **Privilege evidence:** root is used by `install.sh` only for package installation, as the submission contract permits. The original application is exercised by official CI under its ordinary runner ([test.yml:59][ciworkflow] uses sudo only for installation; build/start/test use the next ordinary shell step); no PostgreSQL root-guard patch is included in these 35 files. Some earlier local same-host diagnostics used sandbox UID 0 and a diagnostic PostgreSQL patch: those runs are nonofficial performance diagnostics, not evidence of ordinary-user execution or an official score.
- **Optional ordinary-UID local hold:** blocked during preflight, before starting PostgreSQL, the server or load generation. This sandbox maps only UID/GID 0 (`0 0 1`), has zero capability sets and `NoNewPrivs=1`. Switching to UID 65534 failed: `setpriv` returned EINVAL from setresuid, and `runuser` could not set groups. No mapping/capability workaround or root-run substitute was attempted; there is **no measurement result** for that optional hold. Official ordinary-runner CI remains the execution evidence.
- This is a source/rules audit plus verification of existing official CI metadata. It does not replace organizer review or the official five-minute scored run.
